# Reference

The agent covers all six AWS Well-Architected pillars. Static and CloudFormation rules are grouped by pillar; in V2 mode each pillar has a dedicated reviewer node.

## CLI: `aws-arch-agent`

| Option | Default | Description |
|--------|---------|-------------|
| `--repo`, `-r` | — | Path to repo (required unless `--templates` is set; then repo defaults to templates path) |
| `--out`, `-o` | `report.md` | Output report path |
| `--mode` | `v1` | `v1` (rules + optional [LLM review](#llm-review)) or `v2` (multi-agent + synth) |
| `--iac` | `auto` | IaC source: `auto`, `cdk`, `cloudformation`, or `terraform`. `auto` detects it: CDK wins when `cdk.json` or a CDK package is present; otherwise CloudFormation templates (`AWSTemplateFormatVersion` or an `AWS::` resource) and Terraform (`*.tf`, `*.tf.json`) are detected, and both together are `mixed`. An explicit source with no matching files exits 1 (`cdk` needs `cdk.json`, a CDK package, `bin/*.ts`, or `app.py`). With `--mode v2`, `terraform` exits 1 and `cloudformation` without `--templates` (flag or config `templates`) exits 1 |
| `--tf-plan` | — | `terraform show -json` output (a plan or a state). V1 Terraform scans only. Known planned values replace arguments that depend on `var`, `local`, or another expression, by resource address. Unknown values stay unresolved. Indexed instances (`count`, `for_each`), data sources, and child modules are not read. With one root module, the plan applies to it wherever the plan file is. With several, it applies to the one that holds the plan file. A missing or unreadable plan, or a plan that matches no root module, is a report warning (exit 2) and the scan runs without it. `--mode v2` with `--tf-plan` exits 1 |
| `--max-files` | `400` | Cap on files walked. Rules search only these files |
| `--config` | (auto-detect) | Path to config file |
| `--format`, `-f` | `markdown` | `markdown`, `json`, `sarif`, or `html`. `html` writes one self-contained page (inline CSS and script, no external assets, dark theme) to open in a browser. Each finding links to AWS documentation. With `--enforce-baseline` it labels each finding Accepted or New. `--out` still defaults to `report.md`, so pass a `.html` path. An unknown format fails the run and writes no report |
| `--fail-on` | `none` | Exit 1 if any finding at or above: `high`, `medium`, `low`, `none` |
| `--no-llm` | `false` | Make no LLM calls: no verdicts, no hypotheses. See [LLM review](#llm-review) |
| `--llm-mode` | `full` | V2 only: `full` (one verdict call per pillar with findings) or `compact` (one verdict call). Either way, plus one hypothesis call |
| `--templates` | — | Path to CloudFormation templates (dir or file); V2 only, skips cdk synth |
| `--no-synth` | `false` | Do not run cdk synth; V2 only (static only or with `--templates`) |
| `--rag` | — | Path to RAG doc (V2 only) |
| `--suggestions` | — | Write findings JSON to this path |
| `--baseline` | `.aws-arch-agent-baseline.json` | Path to baseline suppressions file |
| `--enforce-baseline` | `false` | Only fail on findings not in baseline |
| `--update-baseline` | `false` | Add current findings to baseline file |
| `--region` | detected | AWS region whose on-demand prices cost estimates use, for every stack (config `region`). Without it each stack is priced in its own region, then `AWS_REGION`, then `us-east-1`: see [Price region](#price-region). Prices come from a snapshot shipped in the package, so the scan makes no network call. The report states the region and the AWS price list date. A region the snapshot lacks gives no estimates, and the run says so. See [Prices](#prices) |
| `--theme` | — | Only report rules in these themes. Repeatable or comma-separated: `finops`, `security-baseline`, `identity`, `data-protection`, `network-exposure`, `resilience`, `observability`, `sustainability` |
| `--group-by` | `severity` | Group Markdown findings by `severity` or `theme` |
| `--version` | — | Print the version and exit. The version is the release tag the rules come from |

## IaC sources

| `--iac` | What V1 scans |
|---------|---------------|
| `cdk` | CDK TypeScript/Python source with the static rules. Needs `cdk.json`, a CDK package, `bin/*.ts`, or `app.py`. |
| `cloudformation` | Raw templates in the repo (JSON or YAML with `AWSTemplateFormatVersion` or an `AWS::` resource) with the `CF-*` checks. No synth. |
| `terraform` | Root-module `*.tf` / `*.tf.json` with the `CF-*` checks. Findings point at the HCL file and line (approximate for `*.tf.json`). |
| `auto` | CDK when its markers exist; otherwise CloudFormation, Terraform, or both (`mixed`). A repo with none of these falls back to `cdk`. |

**Terraform** is read without `terraform init`, and only root modules are scanned. Local child modules (`source = "./..."`) are skipped and listed under `terraform_child_modules_skipped` in the JSON report's `context.notes`. Remote modules are not fetched. An argument set from `var.*` or `local.*` is unresolved, so no check reports on it. To resolve those values, pass a plan with `--tf-plan`:

```bash
terraform -chdir=infra plan -out=tfplan
terraform -chdir=infra show -json tfplan > infra/plan.json
aws-arch-agent --repo . --iac terraform --tf-plan infra/plan.json --no-llm
```

**V2** synth stays the CDK path. For CloudFormation, use V1, or V2 with `--templates`. For Terraform, use V1. When `--iac auto` detects a non-CDK repo in V2 without `--templates`, the console prints a note. The scan still runs the CDK path, and the exit code does not change.

## Modes

- **V1** (default): static rules over CDK source, or `CF-*` checks over CloudFormation and Terraform. No synth, finishes in seconds.
- **V2**: runs `cdk synth`, then a LangGraph pipeline with six pillar reviewers checks the CloudFormation output. Install with `pip install -e ".[v2]"`. `--llm-mode full` (default) makes one verdict call per pillar with findings. `--llm-mode compact` makes one. See [LLM review](#llm-review).

## LLM providers

LLM output is optional. `--no-llm` skips it.

| Variable | Purpose |
|----------|---------|
| `LLM_PROVIDER` | `ollama` (default) or `selfhosted`. Any other value makes no call and reports `fallback` |
| `OLLAMA_HOST`, `OLLAMA_MODEL` | Ollama server and model (e.g. `llama3:8b`) |
| `OLLAMA_NUM_CTX` | Ollama context size in tokens. Default `24576`, which fits the largest verdict and hypothesis prompts. Ollama silently cuts a longer prompt, so a smaller value uses less memory and can lose part of the prompt. An OpenAI-compatible server sets its own context |
| `LLM_BASE_URL`, `LLM_MODEL` | OpenAI-compatible server (vLLM, llama.cpp, LM Studio, LocalAI) and model. The URL ends before `/chat/completions`, e.g. `http://localhost:8000/v1` |

Cloud LLM providers are not supported. Prompts include source code around each finding and go to the server these settings name, so point them at infrastructure you control. The tool does not check where that server runs, and it sends no API key.

## LLM review

Rules decide the findings. The model adds two things, and neither is a finding:

| | Verdict | Hypothesis |
|---|---------|------------|
| What it is | A label on a finding: `confirmed`, `likely false positive`, or `unsure`, with a reason | A catalog rule the model thinks the scanner missed, in a file with no finding |
| Checked by | The rule that produced the finding | Nothing. It is unverified |
| Report | `LLM verdict:` on the finding | `## Unverified hypotheses`, outside the findings. On the HTML page, outside the severity tabs |
| JSON | `verdict` on the finding | `hypotheses`, each with `"unverified": true` |
| Status | `llm` | `hypotheses_llm` |

Neither changes the severity, the findings list, the summary, the exit code, `--fail-on`, the baseline, or SARIF. A finding labelled `likely false positive` still fails the build.

**Verdicts.** A label appears only when `llm.status` is `ok`. That needs every verdict batch to answer, so a connection failure (`fallback`) or a reply that is not JSON (`invalid`) labels nothing, and the findings match a `--no-llm` run. A verdict for an unknown finding id is dropped. V1 judges at most 100 findings, highest severity first. A verdict prompt holds at most 48,000 characters. When a batch is long, each finding gets less evidence and a narrower source window around its line, down to none.

**Hypotheses.** One call after the rules, when the LLM is on and the verdict calls did not fail. The prompt has the rule catalog (ids and titles), the rule ids already reported, and up to 24,000 characters of IaC files with no finding. V2 adds the synth summary. A hypothesis must give `rule_id`, `file`, `line`, and `why`. It is dropped when the rule id is not in the catalog, the file or line was not in the prompt, or a finding is on that file and line. At most 20 are kept. The catalog leaves out what `rules.include`, `rules.exclude`, and `rules.org` turned off, so a hypothesis cannot name those rules. It is not limited by source, so it can name a rule that this kind of scan does not run: a CDK scan can cite a `CF-*` rule. A hypothesis is also dropped when its rule fired in `cdk.out`, because such a finding cannot be tied to one source file.

A failed hypothesis call has its own status and console line. It keeps the verdicts, and `llm.status` stays `ok`.

## HTML report

`--format html` writes one file to open in a browser. CSS and script are inline and nothing external loads, so it works offline and as a CI artifact. The page has a dark theme, severity counts, All/High/Medium/Low tabs, and each finding's file and line, evidence, recommendation, and suggested code. Each finding links to the AWS docs page for its control (for example S3 default bucket encryption, not the S3 start page) and to the Well-Architected best practice it supports (for example SEC08-BP02 Enforce encryption at rest). The map is `aws_arch_agent/report/doc_topics.py`; `python scripts/check_doc_links.py` checks that every page still exists. A finding with no entry there gets a service start page when its title names a service, and always the pillar overview. The HTML report has no summary section; the summary is in Markdown and JSON. It does list the [Well-Architected answers](#well-architected-answers). These links are the only external URLs on the page, and they load only when clicked. Evidence and code from the scanned repo are escaped. With `--enforce-baseline`, each finding is labeled Accepted or New.

## GitHub Action

Use the composite action, pinned to a release tag (`@main` changes with every merged check; see the README's CI section). It runs on Linux, macOS, and Windows runners and installs ripgrep if the runner lacks it:

```yaml
- uses: gutehall/aws-arch-agent/.github/actions/aws-arch-agent@v0.1.1
  with:
    repo: .
    fail-on: high
    format: json
    no-llm: "true"
    enforce-baseline: "true"
    baseline: .aws-arch-agent-baseline.json
```

For SARIF upload to GitHub Code Scanning, set `format: sarif` and use `github/codeql-action/upload-sarif`.

## Rules

Static and CloudFormation rule IDs, titles, and pillar groups are in [CF_RULES.md](CF_RULES.md). That is the full list. This page does not keep a second copy.

**Repo-level rules (`REPO-*`).** Seventy-nine rules read the repository tree instead of one IaC file, so they run on CDK, CloudFormation, and Terraform scans alike (V1 and V2). REPO-001 to REPO-003 answer OPS 5; REPO-004 to REPO-006 answer SEC 1; REPO-007 and REPO-008 answer SEC 10; REPO-009 to REPO-011 answer SEC 11; REPO-012 and REPO-013 answer REL 1; REPO-014 answers REL 2; REPO-015 answers REL 4; REPO-016 and REPO-017 answer REL 12; REPO-018 to REPO-020 answer OPS 4; REPO-021 and REPO-022 answer OPS 6; REPO-023 to REPO-026 answer REL 8; REPO-027 to REPO-030 answer OPS 8; REPO-031 and REPO-032 answer SEC 3; REPO-033 answers SEC 4; REPO-034 to REPO-036 answer SEC 5; REPO-037 and REPO-038 answer SEC 6; REPO-039 and REPO-040 answer SEC 7; REPO-041 answers SEC 8; REPO-042 to REPO-044 answer REL 5; REPO-045 to REPO-048 answer REL 6; REPO-049 and REPO-050 answer REL 7; REPO-051 answers REL 9; REPO-052 to REPO-055 answer REL 13; REPO-056 answers REL 10; REPO-057 to REPO-059 answer REL 11; REPO-060 to REPO-062 answer PERF 2; REPO-063 answers PERF 3; REPO-064 to REPO-068 answer PERF 4; REPO-069 to REPO-072 answer COST 3; REPO-073 to REPO-079 answer COST 1. The walk includes test directories and skips `node_modules`, `cdk.out`, `.git`, `dist`, `build`, `.venv`, `venv`, `.terraform`, and caches. `rules.include` and `rules.exclude` apply as usual.

- `REPO-001` Repo has no automated tests (OPS05-BP02): no code under `test/`, `tests/`, `__tests__/` or `spec/`, no `*.test.ts`, `*.spec.js`, `test_*.py`, `*_test.py`, `*_test.go` or `*.tftest.hcl` file, no taskcat config, and no cfn-guard rule tests (`*_tests.yaml` next to a `.guard` file).
- `REPO-002` No CI workflow or pipeline builds the workload (OPS05-BP04, OPS05-BP10): no `.github/workflows/*.yml`, `.gitlab-ci.yml`, `buildspec*.yml`, `Jenkinsfile`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `.circleci/config.yml`, `.buildkite/` or `.travis.yml`, and no CodePipeline in the IaC (`AWS::CodePipeline::Pipeline`, `aws_codepipeline`, `codepipeline.Pipeline`, `pipelines.CodePipeline`).
- `REPO-003` Only one environment is defined (OPS05-BP08): fewer than two distinct environments (prod, staging, dev and the synonyms in `rules/environments.py`) named in IaC paths (Terraform, tfvars, CloudFormation templates, `*param*` files), CDK stack and stage ids, or `cdk.json` context keys. Test directories and CDK feature flags do not count; `envs/test` does. Environments built in a loop or read from a variable are not seen.
- `REPO-004` No organization guardrails in the scanned IaC (SEC01-BP01): no service control policy (`AWS::Organizations::Policy`, `aws_organizations_policy` or `organizations.CfnPolicy`, with `SERVICE_CONTROL_POLICY` in the file or no other policy type named, since Terraform defaults to it), no Control Tower control or landing zone (`AWS::ControlTower::EnabledControl`, `AWS::ControlTower::LandingZone`, `aws_controltower_control`, `aws_controltower_landing_zone`, `controltower.CfnEnabledControl`), no organization trail (`IsOrganizationTrail: true`, `is_organization_trail = true`, `isOrganizationTrail: true`), and no Organizations account or OU (`AWS::Organizations::Account`, `AWS::Organizations::OrganizationalUnit`, the Terraform and CDK equivalents). It is an org-level rule: off unless `rules.org` is true or it is listed in `rules.include`, so on an app stack SEC01-BP01 reads not checked and SEC 1 is not met.
- `REPO-005` Account is defined without a security baseline (SEC01-BP06): the IaC defines an account (`AWS::Organizations::Account`, `aws_organizations_account`, `organizations.CfnAccount`, a Service Catalog provisioned product of `AWSControlTowerAccountFactory`, or an AFT `aft-account-request` module) and lacks one or more of a CloudTrail trail, an AWS Config recorder, a GuardDuty detector, Security Hub (`AWS::SecurityHub::Hub`, `aws_securityhub_account`, `securityhub.CfnHub`) and an IAM Access Analyzer. The evidence names the missing services. A repo that defines no account gets no finding: a workload stack does not own the baseline.
- `REPO-006` Account baseline does not check root MFA or root access keys (SEC01-BP02, the root user best practice, so it answers SEC 1): the IaC defines an account (as for REPO-005) and has none of: both AWS Config managed rules `ROOT_ACCOUNT_MFA_ENABLED` (or `ROOT_ACCOUNT_HARDWARE_MFA_ENABLED`) and `IAM_ROOT_ACCESS_KEY_CHECK`, a Config conformance pack, Security Hub with the CIS or FSBP standard (a hub counts unless `EnableDefaultStandards` is false, since the default standards include both controls), or an SCP with an `aws:PrincipalArn` condition on `arn:aws:iam::*:root`. The evidence names the missing Config rules. A repo that defines no account gets no finding.
- `REPO-007` No forensic capture is automated for security findings (SEC10-BP03): no Amazon Detective behavior graph (`AWS::Detective::Graph`, `aws_detective_graph`, `detective.CfnGraph`), and not both of: an EventBridge rule (`AWS::Events::Rule`, `aws_cloudwatch_event_rule`, `events.Rule`, `events.CfnRule`) in a file that names a security finding source (`aws.guardduty`, `aws.securityhub`, `aws.inspector2`, `aws.macie`, `GuardDuty Finding`, `Security Hub Findings - Imported`), and a capture action anywhere in the IaC or code (`CreateSnapshot`, `CreateSnapshots`, `create_snapshot`, `createSnapshot`, or the SSM documents `AWS-CreateSnapshot`, `AWS-CreateImage`, `AWSSupport-CollectEC2*`, `AWSSupport-ContainEC2Instance`). The rule and the capture are not linked target by target, so a backup Lambda that calls `CreateSnapshot` also counts. Org-level: off unless `rules.org` is true or it is listed in `rules.include`, so on an app stack SEC10-BP03 reads not checked and SEC 10 is not met.
- `REPO-008` No containment control is deployed (SEC10-BP06): no security group whose logical id, name, description or tags (near the declaration) say quarantine, isolation, isolate, forensic or containment (`PRIVATE_ISOLATED` subnets do not count), no SSM containment runbook (`AWSSupport-ContainEC2Instance`, `AWS-DisablePublicAccessForSecurityGroup`, an `AWS*-Revoke*` runbook), and no credential revocation (`AWSRevokeOlderSessions` or an `aws:TokenIssueTime` deny, `DeleteLoginProfile`, or `UpdateAccessKey` with `Inactive` in the same file). Org-level, like REPO-007.
- `REPO-009` The build does not scan dependencies (SEC11-BP02): the build configs (the CI files REPO-002 recognises, CodeBuild buildspecs and CDK pipeline steps inline in the IaC: `AWS::CodeBuild::Project`, `aws_codebuild_project`, `BuildSpec.fromObject`, `ShellStep`, `CodeBuildStep`, and the package.json scripts those run with `npm run`, `yarn` or `pnpm`) hold no dependency scan that can fail the build: `npm`/`yarn`/`pnpm audit`, `pip-audit`, `safety check`, `osv-scanner`, `snyk test`, `trivy fs` or `trivy repo` (with a non-zero `--exit-code`), `grype dir:` (with `--fail-on`), OWASP dependency-check (with a failing CVSS score), `cargo audit`, `govulncheck`, `bundler-audit`, `actions/dependency-review-action`, or Amazon Inspector (`inspector-sbomgen` and `inspector-scan`, or the Inspector scan action with a `vulnerability_threshold_exceeded` gate). A scan whose failure is swallowed (`|| true`, `|| exit 0`) or whose step, job or phase may fail (`continue-on-error: true`, `allow_failure: true`, `ignore-errors: true`, `on-failure: CONTINUE`) does not count, and the evidence says so. A repo with no build at all also fires.
- `REPO-010` Container or function artifacts are not scanned before deploy (SEC11-BP02): when the repo builds container images (a `Dockerfile` or `Containerfile`, `AWS::ECR::Repository`, `aws_ecr_repository`, `ecr.Repository`, `ContainerImage.fromAsset`, `DockerImageAsset`, `DockerImageFunction`, or `docker build` in a build config), they need ECR scan on push (`ScanOnPush`, `scan_on_push`, `imageScanOnPush`), ECR registry scanning (`AWS::ECR::RegistryScanningConfiguration`, `aws_ecr_registry_scanning_configuration`), Amazon Inspector with `ECR` (`aws_inspector2_enabler`, or an `Inspector2` enable custom resource, since CloudFormation has no enabler), or a CI image scan that can fail the build (`trivy image`, `grype <image>`, `docker scout cves`, `snyk container test`, `aws ecr start-image-scan`, Amazon Inspector). When it deploys Lambda functions (`AWS::Lambda::Function`, `AWS::Serverless::Function`, `aws_lambda_function`, `lambda.Function`, `NodejsFunction`, `PythonFunction`), they need Amazon Inspector with `LAMBDA` or `LAMBDA_CODE`, or a REPO-009 dependency scan. The evidence names the unscanned kind. No images and no functions, no finding.
- `REPO-011` Packages are not pulled through a central repository (SEC11-BP05): the repo has a package manifest (`package.json`, `requirements*.txt`, `pyproject.toml`, `Pipfile`, `go.mod`, `pom.xml`, `build.gradle`) and no AWS CodeArtifact repository in the IaC, no `aws codeartifact login` in a build, and no registry other than the public default in `.npmrc` (`registry=`), `.yarnrc` or `.yarnrc.yml` (`npmRegistryServer`), `pip.conf` or `pip.ini` (`index-url`), a requirements `--index-url`, a poetry or uv source in `pyproject.toml`, a Maven `<repository>` or `<mirror>`, a Gradle `maven { url }`, or `GOPROXY`, `PIP_INDEX_URL` or `npm config set registry` in a build. Scoped npm registries (`@scope:registry=`) do not count.
- `REPO-012` No Service Quotas usage alarm for the services the stack uses (REL01-BP04): the IaC uses a service with per-account quotas a busy stack reaches (Lambda: `AWS::Lambda::Function`, `AWS::Serverless::Function`, `aws_lambda_function`, `lambda.Function`, `NodejsFunction`, `PythonFunction`, `DockerImageFunction`; Elastic IPs: `AWS::EC2::EIP`, `aws_eip`, `ec2.CfnEIP`; NAT gateways: `AWS::EC2::NatGateway`, `aws_nat_gateway`, `ec2.CfnNatGateway`, `NatProvider.gateway`, or a CDK `natGateways` of 1 or more; load balancers: `AWS::ElasticLoadBalancingV2::LoadBalancer`, `AWS::ElasticLoadBalancing::LoadBalancer`, `aws_lb`, `aws_alb`, `aws_elb`, `ApplicationLoadBalancer`, `NetworkLoadBalancer`, the `*LoadBalanced*` patterns) and has none of: a CloudWatch alarm (`AWS::CloudWatch::Alarm`, `aws_cloudwatch_metric_alarm`, `cloudwatch.Alarm`, `createAlarm`) in a file that names the `AWS/Usage` namespace, `SERVICE_QUOTA()` metric math, the Quota Monitor for AWS solution (`quota-monitor` named in the IaC), or an EventBridge rule in a file that names `aws.trustedadvisor`. The evidence names the services found. A CDK `Vpc` that takes the default NAT gateways (no `natGateways` set) is not seen as using NAT. Quotas are per account, so this is an org-level rule: off unless `rules.org` is true or it is listed in `rules.include`, so on an app stack REL01-BP04 reads not checked.
- `REPO-013` Limits the IaC sets leave no room for failover (REL01-BP06): sums the literal limits written in the IaC across the repo against the default quotas (`DEFAULT_QUOTAS` in `rules/repo_practices.py`, from the Lambda and Amazon VPC quotas pages). Lambda reserved concurrency (`ReservedConcurrentExecutions`, `reserved_concurrent_executions`, `reservedConcurrentExecutions`) fires over 450: the default Regional quota is 1,000 with 100 always unreserved, so 900 can be reserved, and a failover that doubles the load needs half of it free. Elastic IPs (`AWS::EC2::EIP`, `aws_eip`, `ec2.CfnEIP`, plus a CDK VPC's `natGateways: n`, each of which allocates one) fire at 3 or more of the default 5 per Region. CloudFormation and Terraform NAT gateways take their address from an EIP resource, which is counted already. Values from variables, parameters, `count` or `for_each`, or loops are not summed: each literal counts once where it is written. An account with raised quotas may get a false positive. NAT gateways per Availability Zone (default 5) are not checked: a NAT gateway's zone comes from a subnet reference, or from `maxAzs` and the environment, which a text scan does not resolve.
- `REPO-014` VPC CIDR ranges overlap (REL02-BP05): the literal IPv4 CIDRs of VPCs across the repo, from CloudFormation (`AWS::EC2::VPC` and `AWS::EC2::VPCCidrBlock` `CidrBlock`), Terraform (`aws_vpc` and `aws_vpc_ipv4_cidr_block_association` `cidr_block`, and `cidr` on a `terraform-aws-modules/vpc` module) and CDK (`ec2.IpAddresses.cidr()`, `cidr` on `ec2.Vpc`, `cidrBlock` on `CfnVPC` and `CfnVPCCidrBlock`). Any two declarations whose ranges overlap fire, in one file or across stacks and modules, and the evidence names both. Files for different environments (the words in `rules/environments.py` in the path, such as `envs/dev` and `envs/prod`) are not compared, since those networks are not connected. A compiled `.js` next to its `.ts` counts once. CIDRs from variables, parameters, tfvars or IPAM are not seen.
- `REPO-015` Queue and stream workers have no idempotency key or dedupe store (REL04-BP04): the IaC gives a Lambda function a queue or stream event source (`AWS::Lambda::EventSourceMapping`, `aws_lambda_event_source_mapping`, CDK `SqsEventSource`, `KinesisEventSource`, `DynamoEventSource`, `ManagedKafkaEventSource`, `CfnEventSourceMapping` or `addEventSourceMapping`, or a SAM `SQS`, `Kinesis`, `DynamoDB`, `MSK` or `MQ` event) and neither the IaC nor the function code outside tests (Python, TypeScript, JavaScript, Java, Kotlin, C#, Go) has Powertools idempotency (`aws_lambda_powertools.utilities.idempotency`, `@idempotent`, `idempotent_function`, `@aws-lambda-powertools/idempotency`, `makeIdempotent`, the Java and .NET packages, `@Idempotent`, `[Idempotent]`), an SQS FIFO queue with content-based deduplication or a `MessageDeduplicationId`, or a conditional write (`attribute_not_exists` in a file with a `ConditionExpression`). The evidence names the event sources found. It is repo-wide: one control anywhere passes every worker.
- `REPO-016` No fault injection experiment targets the workload (REL12-BP04): no AWS FIS experiment template in the IaC outside tests (`AWS::FIS::ExperimentTemplate`, `aws_fis_experiment_template`, `fis.CfnExperimentTemplate`), and no build (the configs REPO-009 reads, and the package.json scripts they run) that starts one (`aws fis start-experiment`) or runs a chaos tool (`litmusctl`, Chaos Mesh, `gremlin attack`, Chaos Toolkit `chaos run`). What the template targets, and whether it runs on a schedule, is not read.
- `REPO-017` No load test runs in the pipeline (REL12-BP03): no build (CI configs, inline buildspecs, CodeBuild projects and pipelines in the IaC, and the package.json scripts they run) runs a load test tool: `k6 run` or `k6 cloud` (and the Grafana k6 actions), `artillery run`, `locust` with `--headless`, `jmeter -n`, Gatling (`gatling:test`, `gatlingRun`, `gatling.sh`), `vegeta attack`, `hey` or `ab` with `-n`, Taurus `bzt`, or Distributed Load Testing on AWS (`distributed-load-testing`, `DistributedLoadTesting`). ## Prices

Cost estimates read `aws_arch_agent/pricing/prices.json.gz`, an offline snapshot of the AWS Price List bulk API: on-demand USD prices for the resources the cost rules touch (EC2 and RDS instance types, NAT gateway hour and GB, EBS gp2/gp3/io2, public IPv4 addresses including Elastic IPs, Lambda, DynamoDB on-demand and provisioned, S3 storage classes, CloudWatch Logs ingestion and storage). Each price carries its region and the publication date of its AWS offer. A tiered price is the first paid tier. An instance type or region the snapshot lacks gives no estimate, never a guess.

### Price region

Each stack (one template, or one Terraform root module) is priced in one region, the first of:

1. `--region` or config `region`, for every stack.
2. The region the stack's code deploys to: the CDK stack's `env` region (from `cdk.out/manifest.json`; an env-agnostic stack has none), the default `provider "aws"` region in Terraform (a literal, `var.<name>` with a default, or from `--tf-plan`), or else the availability zones written in the template (`eu-north-1a`) when they all name one region.
3. `AWS_REGION`, then `AWS_DEFAULT_REGION`.
4. `us-east-1`.

The report's Prices line names each region and what decided it, for example `eu-north-1 (CDK stack env; AWS price list of 2026-11-05)`. The cost table has a Region column. JSON `context.notes.prices.regions` lists them with their `source`. CDK source scanned without synth has no stacks to read, so it uses steps 1, 3 and 4.

The snapshot covers `us-east-1`, `us-west-2`, `eu-west-1`, `eu-central-1` and `eu-north-1`. A stack in another region gets no estimates, and the run says so. To refresh the snapshot, or to add regions:

```bash
python scripts/refresh_prices.py --regions us-east-1 eu-north-1 --cache-dir /tmp/offers
```

The script streams the offer files (the EC2 one is about 300 MB per region) and writes the same file for the same offers. `--cache-dir` keeps the downloads so a rebuild needs no network. A price two offer rows disagree on stops the build.

## Report summary

Markdown reports open with a **Summary** built from the findings alone, so it is the same with `--no-llm` and the same on every run. It appears in Markdown, and as `summary` in JSON. The HTML report leaves it out:

- **Top fixes**: the five most important fixes. A fix is one rule, covering every resource it reported. They are ranked by severity, then estimated monthly saving, then how many resources the fix covers, then rule id.
- **By pillar**: one line per finding category with its count by severity and possible savings, for example "Cost Optimization: 7 findings (7 Low), about $120.00/month possible savings (estimate)". The lines add up to the findings below, counts and savings alike.
- **Quick wins**: fixes with suggested code and low effort.

## Well-Architected answers

After the summary, every report answers all 57 questions of the current Well-Architected Framework: one line per question, **met** or **not met**, with the findings under it. It appears in Markdown and HTML, and as `answers` in JSON. The answer is computed from the findings alone. Nobody is asked anything, and in V2 the LLM does not change it.

- A question is **met** when every one of its best practices is checked by a rule that ran in this scan, and no finding falls under it.
- Otherwise it is **not met**, and the line says why: how many findings, and how many of its best practices this scan did not check. A missing control is a finding, so a missing control means not met.
- A best practice is not checked when no rule checks it yet, or when its rules did not run: CDK source rules on a CloudFormation or Terraform scan, template checks on a CDK scan without synth or `--templates`, or rules turned off by `rules.include`, `rules.exclude`, or `rules.org`. `--theme` keeps only the rules in those themes. A `severity_threshold` above Low can hide any finding, so with one nothing is met.

The questions and best practices are in `aws_arch_agent/rules/data/well_architected.json` (from the framework's [appendix](https://docs.aws.amazon.com/wellarchitected/latest/framework/appendix.html)). `aws_arch_agent/rules/wa_map.py` says which best practices each rule checks, one question per rule; CDK, CloudFormation, and Terraform scans read the same table. Each finding carries `question` (for example `SEC 8`) and `best_practices` (for example `SEC08-BP02`). `NOT_CHECKED` in the same file lists the best practices no rule checks yet; `tests/test_well_architected.py` fails when a best practice is in neither table, so CI fails on a best practice with no rule.

Each finding has an `effort` field. `low` means one property, changed in place (versioning, log retention, tracing, gp2 to gp3, NoEcho, a tag). `high` means the fix replaces the resource or changes its design (encrypting an existing database or volume, NAT traffic, a public EKS endpoint). Everything else is `medium`. The map is `aws_arch_agent/rules/effort.py`.
